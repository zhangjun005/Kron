> 读者：实现者、维护者、AI 编程助手。
> 前置阅读：[00-总览与架构.md](./00-总览与架构.md) § 6.3、[03-双源同步机制.md](./03-双源同步机制.md)

## 1. 目标与职责

### 1.1 一句话目标

**守护进程 = 唯一的中枢调度器。** 它把所有"被动响应"变成"主动响应"：文件一改，5 分钟内同步；定时任务一触发，扫描和落盘就跑。

### 1.2 守护进程做什么 / 不做什么

| 做 ✅ | 不做 ❌ |
|------|-------|
| 监听 `VERTEX/*/*.md` / `important/**` / `.git/{HEAD,refs,index}` | 不监听 `kron-internal/**`（自家文件自己改）|
| 调度 5 分钟扫描、1 小时自检 | 不提供 HTTP/Socket 接口给外部 |
| 处理 MD 变化 → 更新 tags 镜像 | 不主动推送 webhook/事件给 AI |
| 处理 important 变化 → 触发双源同步 | 不阻塞调用方（不接 IPC 请求）|
| 处理 Git ref 变化 → 重算 vertex 关系 | 不渲染 UI（GUI 进程独立）|
| 写日志、错误恢复、看门狗 | 不解析 Git 内部细节（委托给 `git` CLI）|

**核心原则（与 Git 对齐）**：按需被 CLI/GUI 启动；不主动通知；纯被动响应。AI Agent 通过 `kron <cmd>` 查询状态，不需要也不应该直连守护进程（详见 03 § 5A）。

### 1.3 进程边界（与 GUI/CLI 的关系）

```
┌─────────────────────────────────────────────────────────────┐
│                       文件系统                              │
│  KRON/VERTEX/*/*.md   important/**   .git/*   kron-internal/ │
└──────────▲──────────────▲──────────────▲────────────────────┘
           │              │              │
   监听    │              │              │   监听
           │              │              │
     ┌─────┴──────────────┴──────────────┴─────┐
     │             kron-daemon                 │  ← 唯一中枢
     │  ┌─────────┐  ┌──────────┐  ┌────────┐  │
     │  │ watcher │  │scheduler │  │ 事件   │  │
     │  │ (notify)│→ │(tokio)   │→ │ 派发器 │  │
     │  └─────────┘  └──────────┘  └────────┘  │
     └────────────────────┬────────────────────┘
                          │ 写文件
                          ▼
                  文件系统（kron-internal/）
                          ▲
                          │ 读文件
                  ┌───────┴────────┐
                  │  GUI / CLI     │  ← 终端用户
                  └────────────────┘
```

**三条铁律**（与 00 § 3.1 一致）：

1. 守护进程是**唯一**的自动化中枢。
2. GUI/CLI **不监听**文件系统（避免重复处理）。
3. 进程间**不直接通信**——通过文件系统间接协作。

## 2. 进程模型

### 2.1 单例约束

**守护进程在每个 Kron 工作区有且仅有一个实例。**

- 启动时检测 PID 文件 + 文件锁（见 § 10）
- 第二个实例启动立即退出（退出码 11 = `AlreadyRunning`，见 00 § 6.5）

### 2.2 进程标识

```rust
// kron-internal/daemon.pid
{
  "pid": 12345,
  "workspace": "E:/works/Kron",
  "started_at": "2026-09-05T17:00:00+08:00",
  "version": "0.1.0",
  "args": ["--foreground"],  // 记录启动参数
  "log_file": "C:/Users/zj/AppData/Local/Kron/daemon.log"
}
```

**用途**：
- CLI 查询：`kron daemon status --json` 读这个文件返回运行状态
- 看门狗：检测 PID 是否还活着（僵尸进程清理）
- 升级：升级 Kron 时先停旧的（读 PID → 发送信号）

### 2.3 生命周期

```
   ┌────────┐
   │ 启动   │  kron daemon start（CLI 命令）
   └────┬───┘
        ▼
   ┌────────────┐  失败（10）→ 写 stderr + 退出
   │ 自检阶段   │  - 检查 kron-internal/ 存在
   │ (init)     │  - 解析 config.json
   └────┬───────┘  - 验证 .kron/ 目录
        ▼
   ┌────────────┐  失败（12）→ 退出
   │ 抢占锁     │  - flock PID 文件
   └────┬───────┘  - 已运行则退出 11
        ▼
   ┌────────────┐
   │ 启动监听   │  - notify::recommended_watcher
   └────┬───────┘  - 注册 6 个路径模式
        ▼
   ┌────────────┐
   │ 启动调度器 │  - tokio interval 5min / 1h
   └────┬───────┘
        ▼
   ┌────────────┐
   │ 主循环     │  - 处理事件 / 调度任务 / 响应信号
   └────┬───────┘
        │
        ▼ 收到 SIGTERM / Ctrl-C / `kron daemon stop`
   ┌────────────┐
   │ 优雅停机   │  - 停止监听器
   │ (shutdown) │  - 等待当前任务完成（最多 30s）
   └────┬───────┘  - 释放锁
        ▼ 删 PID 文件
     退出（0）✓
```

### 2.4 退出码（守护进程专属）

| 退出码 | 含义 | 触发场景 |
|--------|------|---------|
| 0 | 正常退出 | 收到停止信号、用户 Ctrl-C |
| 10 | 初始化失败 | kron-internal/ 缺失、配置损坏 |
| 11 | 已运行 | 单实例锁冲突 |
| 12 | 锁文件失败 | flock 失败（罕见） |
| 13 | 监听器启动失败 | notify 不可用 |
| 14 | 看门狗触发 | 内部 panic 计数超阈值 |
| 1 | 运行时错误 | 其他未捕获错误（看 stderr）|

**注**：这些是**守护进程作为 `kron daemon start` 子命令**的退出码。当守护进程由系统/守护管理器重启时（如 panic 后），重启脚本读这个退出码决定是否放弃。

## 3. 文件监听

### 3.1 技术选型

**用 Rust 生态标准的 [`notify`](https://crates.io/crates/notify) crate（v6+）**。

| 候选 | 评估 |
|------|------|
| **`notify` v6+** ✅ | Windows 用 ReadDirectoryChangesW，macOS 用 FSEvents，Linux 用 inotify。跨平台标准。|
| `hotwatch` | 简单但功能少，活跃度低 |
| 自研轮询 | 跨平台差异大，重造轮子 |
| `fsnotify` | Go 库，不适用 |

**推荐配置**：

```rust
use notify::{Watcher, RecursiveMode, recommended_watcher};

let mut watcher = recommended_watcher(|res| {
    // 回调里只做一件事：发到 mpsc channel
    let _ = tx.send(res);
})?;

watcher.watch(Path::new("KRON/VERTEX"), RecursiveMode::Recursive)?;
watcher.watch(Path::new("KRON/important"), RecursiveMode::Recursive)?;
watcher.watch(Path::new(".git"), RecursiveMode::Recursive)?;
```

### 3.2 监听路径（精确到文件，避免噪音）

来自 00 § 6.3，已验证：

| 路径 | 模式 | 触发事件 |
|------|------|---------|
| `KRON/VERTEX/*/*.md` | Recursive | `MdChanged` |
| `KRON/VERTEX/*/_meta.json` | Recursive | `VertexMetaChanged` |
| `KRON/important/**` | Recursive | `ImportantChanged` |
| `.git/HEAD` | 文件级 | `BranchSwitched` |
| `.git/refs/heads/*` | Recursive | `GitRefChanged` |
| `.git/index` | 文件级 | `GitIndexChanged` |

**不监听的路径**（关键）：

| 路径 | 不监听原因 |
|------|-----------|
| `kron-internal/**` | 守护进程自家写，避免自我触发死循环 |
| `KRON/important/.kron/` | 重要文件的镜像目录，由守护进程维护 |
| `node_modules/`, `target/`, `.venv/` 等 | 项目构建产物，由用户在 `.gitignore` 或 `.kronignore` 排除 |
| IDE 临时文件 | `.swp`, `.tmp`, `~` 等 |

### 3.3 平台差异与坑

| 平台 | 监听器后端 | 已知问题 | 应对 |
|------|----------|---------|------|
| **Windows** | ReadDirectoryChangesW | 单文件超过 1024 个事件会丢失；不支持网络盘 | 加上 § 4 防抖；网络盘禁用守护进程（提示用户）|
| **macOS** | FSEvents | 子目录事件递归触发；文件移动事件可能漏报 | 启用 `RecursiveMode::Recursive`；移动后用 `git status` 兜底 |
| **Linux** | inotify | inotify watch 句柄耗尽（默认 8192）| 启动时检查句柄数；超限警告用户 |

**平台特定配置**：

```rust
#[cfg(target_os = "windows")]
fn platform_specific_setup() -> Result<()> {
    // Windows: 检查网络盘
    if is_network_path("KRON/important")? {
        return Err(KronError::NetworkPathNotSupported);
    }
    Ok(())
}

#[cfg(target_os = "linux")]
fn platform_specific_setup() -> Result<()> {
    // Linux: 检查 inotify 句柄数
    let max = read_fs_max_watches()?;
    let used = current_watch_count();
    if used as f64 / max as f64 > 0.8 {
        warn!("inotify 句柄使用率 >80%，建议调高 fs.inotify.max_user_watches");
    }
    Ok(())
}
```

### 3.4 编辑器/工具的"保存即写"模式

| 工具 | 保存行为 | 守护进程行为 |
|------|---------|------------|
| VSCode | 原子重命名（`foo.md.tmp` → `foo.md`） | 收到 `Remove + Create`，合并为 `Modify` |
| Typora | 原地覆盖 | 收到 `Modify(EventKind::Modify(_))` |
| AI Agent（`Edit` 工具） | 原地写 + rename | 收到 `Modify + Create`，合并 |
| `git checkout` | 工作区文件被覆盖 | 收到 `Modify`，归类为外部修改 |

**关键**：守护进程**不知道也不关心**是谁改的。所有路径都收敛为"文件当前 hash/mtime 变了 → 检查 → 同步"。

## 4. 事件去抖与合并

### 4.1 为什么需要去抖

```
用户保存一个 MD：
  17:00:00.000  write_begin
  17:00:00.020  temp file created
  17:00:00.045  temp file renamed to target
  17:00:00.060  fsnotify event #1: Create
  17:00:00.062  fsnotify event #2: Modify (metadata)
  17:00:00.063  fsnotify event #3: Modify (content)

→ 不去抖：3 次事件，3 次扫描，浪费
```

### 4.2 去抖策略

| 级别 | 时间窗 | 行为 |
|------|--------|------|
| **文件级防抖** | **200ms** | 同一文件 200ms 内多次事件合并为 1 次 |
| **批处理窗** | **1s** | 1s 内的所有事件打包成 1 个 batch |
| **事件合并** | 200ms | 连续 `Create + Modify` 合并为 `Modify` |

**实现**：用 `HashMap<PathBuf, Instant>` 跟踪每文件最后事件时间，tokio interval 200ms 扫描并 flush。

```rust
struct Debouncer {
    pending: HashMap<PathBuf, FileEvent>,  // 最新事件
    last_seen: HashMap<PathBuf, Instant>,  // 最后事件时间
}

impl Debouncer {
    fn ingest(&mut self, event: FileEvent) {
        let path = event.path.clone();
        self.pending.insert(path.clone(), event);
        self.last_seen.insert(path, Instant::now());
    }

    fn flush_due(&mut self, now: Instant) -> Vec<FileEvent> {
        let mut out = Vec::new();
        self.pending.retain(|path, evt| {
            if now.duration_since(self.last_seen[path]) >= Duration::from_millis(200) {
                out.push(evt.clone());
                false
            } else {
                true
            }
        });
        out
    }
}
```

### 4.3 编辑器保存的"惊群效应"

**场景**：用户保存一个大 MD 触发 3 个事件，AI Agent 同时也在改另一个文件。

```
t=0    fsnotify: Create foo.md (from rename)
t=20   fsnotify: Modify foo.md
t=80   fsnotify: Modify bar.md
t=200  Debouncer flushes: foo.md (最新), bar.md
t=200  派发到 handler queue
```

**关键**：bar.md 在 200ms 窗内的事件**不会等待**——它是独立文件，按 200ms 自己计时。

## 5. 事件分类与处理流水线

### 5.1 事件类型（精简到 5 类）

来自 00 § 6.3：

| 事件 | 路径 | 触发源 | 优先级 | Handler |
|------|------|--------|--------|---------|
| `MdChanged` | `VERTEX/*/*.md` | 用户/AI 编辑 | 中 | `md::on_changed` |
| `VertexMetaChanged` | `VERTEX/*/_meta.json` | GUI/CLI 改绑定 | 中 | `vertex::on_meta_changed` |
| `ImportantChanged` | `KRON/important/**` | 外部编辑 | 高 | `sync::on_important_changed`（详见 03 § 5）|
| `GitRefChanged` | `.git/HEAD`, `.git/refs/heads/*` | `git commit/checkout` | 低 | `vertex::on_git_ref_changed` |
| `GitIndexChanged` | `.git/index` | `git add/rm/mv` | 低 | `git::on_index_changed` |

### 5.2 处理流水线（Pipeline）

```
   notify callback
        │  mpsc::Sender<FileEvent>
        ▼
   ┌─────────────┐
   │ Debouncer   │  200ms 防抖 + 事件合并
   └─────┬───────┘
         │  mpsc::Sender<BatchEvent>  (1s 批)
         ▼
   ┌─────────────┐
   │ Classifier  │  按 path 匹配到事件类型
   └─────┬───────┘
         │  mpsc::Sender<DomainEvent>
         ▼
   ┌─────────────┐
   │ Dispatcher  │  按事件类型路由到 handler
   └─────┬───────┘
         │
         ├──► MdChanged       ──► md::on_changed
         ├──► VertexMetaChanged ──► vertex::on_meta_changed
         ├──► ImportantChanged  ──► sync::on_important_changed（→ 03 § 5）
         ├──► GitRefChanged     ──► vertex::on_git_ref_changed
         └──► GitIndexChanged   ──► git::on_index_changed
         
         每个 handler 在 tokio task 里独立跑
```

### 5.3 处理器并发模型

- **每个 handler 是独立的 tokio task**，互不阻塞
- **同一文件的事件串行处理**（用 `HashMap<PathBuf, oneshot::Sender>` 串行化）
- **不同文件并行处理**
- handler panic **不影响其他 handler**（tokio `JoinHandle` + catch_unwind）

```rust
async fn dispatcher_loop(mut rx: mpsc::Receiver<DomainEvent>) {
    let mut inflight: HashMap<PathBuf, JoinHandle<()>> = HashMap::new();
    
    while let Some(event) = rx.recv().await {
        let path = event.path().to_path_buf();
        
        // 等待同一文件的 inflight 任务
        if let Some(handle) = inflight.remove(&path) {
            let _ = handle.await;
        }
        
        // 派发新任务
        let handle = tokio::spawn(async move {
            if let Err(e) = handle_event(event).await {
                error!("Handler error: {e}");
            }
        });
        inflight.insert(path, handle);
    }
}
```

### 5.4 关键 handler 行为约束

**`md::on_changed`**：
- 重新解析 MD 文件（解析成本低，几十微秒）
- 计算 tags，更新 `kron-internal/tags/<file>.json` 镜像
- 如果检测到 task 增删 → 更新 `kron-internal/states/tasks.json`
- **不**直接触发 GUI 刷新（GUI 自己有轮询或 5 分钟检查）

**`sync::on_important_changed`**：
- 调用 03 § 5.1 的 `detect_conflict()` 流程
- 冲突时：写 `kron-internal/conflicts/<id>/`，更新 sync_state
- **不阻塞**，立即返回（见 03 § 5.1）

**`vertex::on_git_ref_changed`**：
- 重算 vertex 关系（哪些 task 在哪个 branch）
- 写 `kron-internal/vertices.json`（汇总索引）

### 5.5 Handler 失败处理

| 失败类型 | 处理 |
|---------|------|
| 解析错误（MD 损坏）| 写日志 + 跳过 + 不影响其他文件 |
| 写文件失败（磁盘满）| 重试 3 次 → 报警到日志 → 标记事件为 failed |
| handler panic | tokio catch_unwind → 计入 panic_count → 超过阈值触发 § 8 看门狗 |
| 单文件反复失败 | 写 `kron-internal/quarantine/<file>.json`，后续跳过 |

## 6. 调度器

### 6.1 调度任务清单

| 任务 | 频率 | 用途 | 实现 |
|------|------|------|------|
| **T1**: 扫描过期文档 | **5 min** | `.kron-context/` 增量更新 | `scheduler::scan_expired_docs` |
| **T2**: GUI 内存落盘 | **5 min** | `states/*.json` 持久化 | `scheduler::flush_gui_state` |
| **T3**: 完整性自检 | **1 h** | config.json 一致性 | `scheduler::integrity_check` |
| **T4**: 清理孤立文件 | **24 h** | 过期 conflicts / 临时文件 | `scheduler::cleanup_orphans` |
| **T5**: 守护进程健康报告 | **1 h** | 写 `daemon.pid` 刷新时间戳 | `scheduler::heartbeat` |

### 6.2 tokio interval 实现

```rust
pub struct Scheduler {
    tx: mpsc::Sender<ScheduledTask>,
}

impl Scheduler {
    pub fn spawn(mut self) {
        tokio::spawn(async move {
            let mut t1 = tokio::time::interval(Duration::from_secs(300));   // 5 min
            let mut t3 = tokio::time::interval(Duration::from_secs(3600));  // 1 h
            let mut t4 = tokio::time::interval(Duration::from_secs(86400)); // 24 h
            let mut t5 = tokio::time::interval(Duration::from_secs(3600));  // 1 h
            
            loop {
                tokio::select! {
                    _ = t1.tick() => self.tx.send(ScheduledTask::ScanExpiredDocs).await?,
                    _ = t3.tick() => self.tx.send(ScheduledTask::IntegrityCheck).await?,
                    _ = t4.tick() => self.tx.send(ScheduledTask::CleanupOrphans).await?,
                    _ = t5.tick() => self.tx.send(ScheduledTask::Heartbeat).await?,
                    Some(cmd) = self.rx.recv() => break, // shutdown signal
                }
            }
        });
    }
}
```

### 6.3 任务重叠处理

**问题**：T1（5 min）和 T4（24 h）可能在同一时刻重叠。

**解决**：
- T1/T2 都用 `SkipIfRunning` 语义：上一个未完成，跳过这次
- T3/T4 用 `RunOneAtATime`：互斥锁
- 实现：`Arc<Mutex<bool>>` 标志位

```rust
async fn run_with_skip(tx: mpsc::Sender<Task>, running: Arc<AtomicBool>) {
    if running.swap(true, Ordering::SeqCst) {
        return; // 上一个还在跑，跳过
    }
    let result = tx.send(ScheduledTask::ScanExpiredDocs).await;
    running.store(false, Ordering::SeqCst);
    result?;
}
```

## 7. 启动与停止

### 7.1 三种启动模式

| 模式 | 命令 | 用途 |
|------|------|------|
| **后台模式** | `kron daemon start` | 默认；fork 到后台，写 PID |
| **前台模式** | `kron daemon start --foreground` | 调试；日志输出到 stderr |
| **系统服务** | Windows 计划任务 / macOS launchd / systemd | 开机自启 |

### 7.2 后台模式实现（Windows）

**Rust 用 [`std::process::Command::spawn`](https://doc.rust-lang.org/std/process/struct.Command.html) + detach**：

```rust
fn spawn_detached(exe: &Path) -> Result<u32> {
    // Windows: 用 DETACHED_PROCESS + CREATE_NEW_PROCESS_GROUP
    #[cfg(target_os = "windows")]
    {
        use std::os::windows::process::CommandExt;
        const DETACHED_PROCESS: u32 = 0x00000008;
        const CREATE_NEW_PROCESS_GROUP: u32 = 0x00000200;
        
        let child = Command::new(exe)
            .arg("daemon")
            .arg("start")
            .arg("--foreground")
            .creation_flags(DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP)
            .stdout(Stdio::null())
            .stderr(Stdio::null())
            .spawn()?;
        
        Ok(child.id())
    }
    
    #[cfg(unix)]
    {
        use std::os::unix::process::CommandExt;
        let child = Command::new(exe)
            .arg("daemon")
            .arg("start")
            .arg("--foreground")
            .stdout(Stdio::null())
            .stderr(Stdio::null())
            .pre_exec(|| {
                // 创建新会话
                Ok(())
            })
            .spawn()?;
        Ok(child.id())
    }
}
```

### 7.3 Windows 开机自启（计划任务）

**用 `taskschd.msc` 注册计划任务**（详见 00 § 6.7）：

```powershell
$action = New-ScheduledTaskAction `
```

### 7.5 优雅停机

**信号处理**：

| 信号 | 平台 | 行为 |
|------|------|------|
| `SIGTERM` | Unix / Windows (Ctrl-C) | 优雅停机 |
| `SIGINT` | Unix | 优雅停机 |
| `Ctrl-C` | Windows console | 优雅停机 |
| `kron daemon stop` | CLI 命令 | 发信号 → 等待 30s → 强杀 |

**优雅停机流程**：

```rust
async fn shutdown_handler(rx: mpsc::Receiver<()>, daemon: Daemon) {
    rx.recv().await;  // 等待信号
    
    info!("收到停机信号，开始优雅关闭");
    
    // 1. 停止接收新事件
    daemon.stop_watcher().await;
    
    // 2. 等待当前 handler 完成（最多 30s）
    let timeout = tokio::time::timeout(Duration::from_secs(30), daemon.drain_handlers());
    if timeout.await.is_err() {
        warn!("部分 handler 未在 30s 内完成，将强制退出");
    }
    
    // 3. 写最终状态
    daemon.write_final_state().await;
    
    // 4. 删 PID 文件
    daemon.remove_pid_file().ok();
    
    // 5. 释放锁
    daemon.release_lock().ok();
    
    info!("守护进程已退出");
    std::process::exit(0);
}
```

## 8. 错误处理与恢复

### 8.1 Panic 隔离

**原则**：单个 handler panic **不影响守护进程整体存活**。

```rust
async fn safe_handler<F, T>(future: F) -> Result<(), String>
where
    F: Future<Output = Result<T>>,
{
    match AssertUnwindSafe(future).catch_unwind().await {
        Ok(Ok(_)) => Ok(()),
        Ok(Err(e)) => Err(format!("handler error: {e}")),
        Err(panic) => {
            let panic_msg = panic.downcast_ref::<&str>()
                .map(|s| s.to_string())
                .unwrap_or_else(|| "unknown panic".to_string());
            error!("Handler panic: {panic_msg}");
            Err(format!("panic: {panic_msg}"))
        }
    }
}
```

### 8.2 看门狗（Watchdog）

**触发条件**：最近 1 小时内 panic_count ≥ 5。

```rust
struct Watchdog {
    panic_timestamps: Mutex<VecDeque<Instant>>,
    threshold: usize,  // 5
    window: Duration,  // 1h
}

impl Watchdog {
    fn record_panic(&self) {
        let mut ts = self.panic_timestamps.lock().unwrap();
        ts.push_back(Instant::now());
        // 清理超过 1h 的
        while let Some(&t) = ts.front() {
            if t.elapsed() > self.window {
                ts.pop_front();
            } else {
                break;
            }
        }
    }
    
    fn should_die(&self) -> bool {
        let ts = self.panic_timestamps.lock().unwrap();
        ts.len() >= self.threshold
    }
}
```

**触发后行为**：
1. 写详细 panic 报告到 `kron-internal/daemon-panic-report.json`
2. 退出码 14（看门狗触发）
3. **由外部监控重启**（计划任务 / launchd / systemd）

### 8.3 关键失败场景与恢复

| 场景 | 失败现象 | 自动恢复策略 |
|------|---------|------------|
| **磁盘满** | 写 `kron-internal/` 失败 | 重试 3 次 → 报警 → 跳过这个事件 → 标记 quarantine |
| **kron-internal/ 被删除** | 写文件失败 | **立即退出 10**（守护进程无法恢复；用户需手动重建目录）|
| **config.json 损坏** | 初始化失败 | 退到默认配置 + 报警；用户决定是否修复 |
| **notify 监听器断连** | 回调不触发 | 5 分钟内重连；失败则退出 |
| **lock 文件残留（僵尸进程）** | 启动失败 | 检测 PID 是否还活着；死进程 → 自动清理锁 |
| **Git 不可用** | `git status` 失败 | 跳过 Git 相关 handler；其他功能继续 |
| **MD 文件损坏（解析失败）** | handler 报错 | 写 `quarantine/`；不阻塞其他文件 |

### 8.4 自我修复的边界

**守护进程自我修复**（不重启即可恢复）：

- ✅ Handler 单次失败重试
- ✅ notify 监听器重连
- ✅ 锁文件清理
- ✅ quarantine 标记

**守护进程自我修复不了**（需要外部重启）：

- ❌ kron-internal/ 被删
- ❌ inotify 句柄耗尽（需要用户调高系统参数）
- ❌ 磁盘满（需要用户清空间）
- ❌ Panic 看门狗触发（守护进程主动退出 14）

### 10.3 锁实现

```rust
use fs2::FileExt;
use std::fs::{File, OpenOptions};

pub struct DaemonLock {
    file: File,
}

impl DaemonLock {
    pub fn acquire(path: &Path) -> Result<Self> {
        let file = OpenOptions::new()
            .create(true)
            .write(true)
            .open(path)?;
        
        match file.try_lock_exclusive() {
            Ok(()) => Ok(Self { file }),
            Err(_) => Err(KronError::AlreadyRunning),
        }
    }
    
    pub fn release(self) -> Result<()> {
        FileExt::unlock(&self.file)?;
        // File 句柄 drop 时自动关闭
        Ok(())
    }
}
```

### 10.4 僵尸进程检测

**启动时**：

```rust
fn is_pid_alive(pid: u32) -> bool {
    #[cfg(target_os = "windows")]
    {
        // Windows: 用 OpenProcess 检查
        use windows::Win32::System::Threading::{OpenProcess, PROCESS_QUERY_LIMITED_INFORMATION};
        unsafe {
            OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION, false, pid).is_ok()
        }
    }
    
    #[cfg(unix)]
    {
        // Unix: kill -0
        unsafe { libc::kill(pid as i32, 0) == 0 }
    }
}

fn handle_stale_lock(pid_file: &Path) -> Result<()> {
    let content = std::fs::read_to_string(pid_file)?;
    let info: PidInfo = serde_json::from_str(&content)?;
    
    if is_pid_alive(info.pid) {
        return Err(KronError::AlreadyRunning);
    }
    
    // PID 不存在 → 僵尸，清理
    warn!("发现僵尸锁，PID {} 已不存在", info.pid);
    std::fs::remove_file(pid_file)?;
    Ok(())
}
```

### 11.1 资源预算

| 操作 | 目标延迟 | 实测 |

### 11.3 性能优化策略
