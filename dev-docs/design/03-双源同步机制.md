# Kron 双源同步机制

> 本文档定义重要文件（Important Files）在"项目内"和"kron-internal"两份存储之间的同步策略、冲突检测算法、冲突解决流程、复原机制。

> 对应架构：dev-docs/design/00-总览与架构.md § 5 双源同步设计

> 对应模块：dev-docs/design/02-模块划分.md § 6.4 SyncStrategy

## 1. 同步对象与目录

### 1.1 什么是"重要文件"

**重要文件 = 被用户显式标记 `kron important add <path>` 的项目内文件**。

Kron 对这些文件提供"双源存储"：一份在原项目目录（用户可见、可被 git 追踪），一份在 `.kron-internal/important/files/<rel_path>`（Kron 内部权威源）。两份内容应当一致。

其它非重要文件 Kron 完全不感知。

### 1.2 双源目录约定

```
<项目根>/
├── .kron/                          ← 项目元数据（单源，git 追踪）
│   └── VERTEX/<name>/
├── .kron-internal/                 ← Kron 内部权威源（单源，git ignore）
│   ├── config.json
│   ├── vertices.json
│   ├── states/<vertex>.json
│   ├── tags/tasks.json
│   ├── important/
│   │   ├── _meta.json              ← ImportantFilesIndex（单源）
│   │   └── files/                  ← 重要文件的 Kron 内部副本
│   │       └── <分类>/<rel_path>   ← 镜像项目内结构
│   ├── conflicts/<id>.json         ← 冲突记录
│   └── restores/<id>.json          ← 复原记录
└── src/
    └── main.rs                     ← 重要文件举例（被 kron important add 标记）
```

### 1.3 不参与同步的目录

Kron **不**自动同步这些目录（与时间同步无关）：

| 目录 | 原因 |
|------|------|
| `.kron/` 全部 | 单源设计，无需双源 |
| `.kron-internal/config.json` 等元数据 | 单源 |
| `.kron/.kron-context/*` | AI 中间文档，不属于"重要文件"范畴 |
| `.kron-internal/conflicts/` | 已备份的冲突，本身就是记录 |
| `.kron-internal/restores/` | 复原记录 |

## 2. 同步架构总览

### 2.1 两份数据各自的角色

| 副本 | 角色 | 谁写 | 谁读 |
|------|------|------|------|
| **项目内**（原位置）| 用户可见；可被 git 追踪；编辑器/IDE 直接编辑 | 用户、编辑器、CLI 复原、守护进程 | 用户、编辑器、CLI、GUI |
| **kron-internal** | Kron 内部权威源；备份；冲突参照系 | CLI add/import、守护进程监听 + 复制、冲突解决后 | CLI status、守护进程扫描、冲突检测 |

### 2.2 双源状态机

对每个重要文件，存在 5 种状态（对应数据模型 `SyncState`）：

```
                    ┌──────────┐
                    │  Synced  │  双源一致
                    └────┬─────┘
                         │
        ┌────────────────┼────────────────┐
        │                │                │
   项目内变      Kron 内部变       两边都变（hash 不同）
        │                │                │
        ▼                ▼                ▼
   ┌──────────┐    ┌──────────┐    ┌──────────┐
   │Internal  │    │ Project  │    │Conflict  │
   │  Only    │    │  Only    │    │(recover) │
   └────┬─────┘    └────┬─────┘    └────┬─────┘
        │                │                │
        └──── 自动同步 ──┴──── 备份+决策 ─┘
                         │
                         ▼
                    ┌──────────┐
                    │ Syncing  │  同步进行中
                    └────┬─────┘
                         │
                         ▼
                    ┌──────────┐
                    │  Synced  │
                    └──────────┘
```

详细解释：

| 状态 | 含义 | 持久化字段 `ImportantFileMeta.sync_state` |
|------|------|------------------------------------------|
| **Synced** | 两边内容相同（hash 相等）| `"synced"` |
| **InternalOnly** | 项目内被删/未同步，Kron 内部还在 | `"internal_only"` |
| **ProjectOnly** | Kron 内部被删/未同步，项目内还在 | `"project_only"` |
| **Conflict** | 两边都变了，且 hash 不同 | `"conflict"` |
| **Syncing** | 正在执行同步（写入临时标志，写完转 Synced/Conflict） | `"syncing"` |

**注**：`InternalOnly` 和 `ProjectOnly` 都不是"冲突"——前者表示项目内被外部删除，后者表示 Kron 内部被外部删除。它们都可通过"用另一边补全"自动修复。

**真正的 Conflict** 只发生在双方都被修改且 hash 不一致时。

### 2.2.1 设计核心：守护进程不阻塞，AI 是决策主体

Kron 的同步机制刻意把"检测冲突"和"解决冲突"解耦：

- **守护进程只负责检测**：发现冲突 → 备份 → 标记 → 发事件 → 立即返回
- **决策由调用方驱动**：AI 通过 CLI 命令（`kron conflict list/show/resolve`）主动查询和解决

这一设计让 **AI 成为一等公民**：AI 工作流中遇到冲突时，可以自主读 diff、自主决策、自主解决，**无需人类介入、无需 GUI**。

具体约定见 § 5.6（CLI 的 AI 友好约定）和 § 5.7（AI 工作流示例）。

### 2.3 同步触发器

| 触发场景 | 频率 | 谁触发 | 同步方向 |
|---------|------|--------|---------|
| 用户执行 `kron important add <path>` | 一次性 | CLI | 项目内 → kron-internal（初次导入） |
| 用户在编辑器修改重要文件 | 高频（秒级）| 守护进程 | 项目内 → kron-internal |
| 用户编辑重要文件后保存 | 高频 | 守护进程 | 项目内 → kron-internal |
| 用户执行 `kron important restore <path>` | 一次性 | CLI | kron-internal → 项目内 |
| 守护进程定时健康检查 | 低频（5 分钟）| 守护进程 | 扫描 + 修正状态机 |
| 守护进程检测到项目内文件被外部删除 | 触发式 | 守护进程 | 标记 InternalOnly，**不自动删 Kron 内部副本**（保护用户数据）|
| 守护进程检测到 Kron 内部副本被外部删除 | 触发式 | 守护进程 | 标记 ProjectOnly，自动从项目内复制恢复内部副本 |
| **AI 通过 CLI 主动查询冲突状态** | 按需 | AI | 不触发同步，仅查询（`kron conflict list/show`）|
| **AI 通过 CLI 主动解决冲突** | 按需 | AI | 不触发检测，仅决策（`kron conflict resolve`）|

> **关键不变式**：守护进程**永远不阻塞等待决策**。冲突检测完成即返回，AI/用户/GUI 通过 CLI 命令（同步调用）主动驱动后续动作。

### 2.4 关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 谁是权威源？ | **kron-internal** 是权威源 | 用户在 GUI/CLI 看到的文件状态以 Kron 内部为准 |
| 项目内被外部删除怎么办？ | **不删 Kron 内部副本**，标记 InternalOnly，提供 `kron important restore` 复原 | 防误删；用户必须显式决定 |
| Kron 内部被外部删除怎么办？ | 自动从项目内恢复（用户已 add 过的，理应有项目内版本） | Kron 内部副本是缓存，可恢复 |
| 冲突备份放哪？ | `kron-internal/conflicts/<id>.json` + 两份字节副本存 `kron-internal/conflicts/<id>/` | 冲突解决前的安全网 |
| 冲突解决超时？ | 不超时，永远 Pending 直到用户决策 | 防自动化丢失数据 |

## 3. 同步算法

### 3.1 单文件同步决策算法

**输入**：`(project_file_meta, internal_file_meta)` —— 来自 `ImportantFileMeta` 索引和文件系统实时探测

**输出**：`SyncDirection` 枚举值

```rust
// kron-sync/src/decision.rs

use kron_core::ports::storage::StorageBackend;
use kron_core::model::sync::{SyncDirection, SyncState};

pub fn decide_sync_direction(
    storage: &dyn StorageBackend,
    project_path: &Path,
    internal_path: &Path,
    recorded: SyncState,
) -> Result<SyncDirection, SyncError> {
    // Step 1: 检查双方存在性
    let project_exists = storage.exists(project_path);
    let internal_exists = storage.exists(internal_path);

    match (project_exists, internal_exists) {
        (false, false) => {
            // 双方都不存在 → 视为已删除，从索引中移除（由调用方处理）
            Ok(SyncDirection::SourceNotFound)
        }
        (true, false) => {
            // Kron 内部缺失 → 从项目内恢复
            Ok(SyncDirection::InternalToProject)
        }
        (false, true) => {
            // 项目内缺失 → 标记 InternalOnly，不自动同步
            Ok(SyncDirection::AlreadySynced) // 调用方会改为 InternalOnly 标记
        }
        (true, true) => {
            // 双方都存在 → 比较 hash
            let project_hash = storage.hash(project_path)?;
            let internal_hash = storage.hash(internal_path)?;

            if project_hash == internal_hash {
                Ok(SyncDirection::AlreadySynced)
            } else {
                // hash 不同 → 需要进一步分析
                compare_by_mtime(
                    storage, project_path, internal_path,
                    project_hash, internal_hash,
                )
            }
        }
    }
}

fn compare_by_mtime(
    storage: &dyn StorageBackend,
    project_path: &Path,
    internal_path: &Path,
    project_hash: String,
    internal_hash: String,
) -> Result<SyncDirection, SyncError> {
    let project_mtime = storage.mtime(project_path)?;
    let internal_mtime = storage.mtime(internal_path)?;

    let diff = project_mtime
        .duration_since(internal_mtime)
        .map(|d| d.as_secs() as i64)
        .unwrap_or_else(|e| -(e.duration().as_secs() as i64));

    // 容差 2 秒，避免文件系统 mtime 精度问题
    if diff.abs() <= 2 {
        // mtime 几乎相等但 hash 不等 → 极小概率事件（同秒内两次写入）
        // 视为 Conflict，要求用户决策
        Ok(SyncDirection::Conflict)
    } else if diff > 0 {
        // 项目内更新 → 项目内 → Kron 内部
        Ok(SyncDirection::ProjectToInternal)
    } else {
        // Kron 内部更新 → Kron 内部 → 项目内
        Ok(SyncDirection::InternalToProject)
    }
}
```

### 3.2 mtime + hash 双重判断的取舍

| 方案 | 优 | 劣 |
|------|----|----|
| **只比较 hash** | 最准确，无歧义 | 每次都计算 hash（MD5 也需读整个文件，大文件慢）|
| **只比较 mtime** | 快 | 跨机器时钟不准；备份恢复后 mtime 失真 |
| **mtime + hash 组合（采用）**| hash 是终极判定，mtime 仅用于方向决策 | 实现稍复杂 |

**采用方案**：先读 mtime 估算方向，**只在不确定时（mtime 差 ≤ 2 秒）才计算 hash** 做最终仲裁。**任何 sync 之前都校验一次 hash**（保险）。

### 3.3 全项目扫描算法

```rust
// kron-sync/src/scan.rs

use kron_core::ports::storage::StorageBackend;
use kron_core::ports::repo::ImportantRepo;
use kron_core::model::sync::{FilePair, SyncDirection};

pub struct ScanResult {
    pub to_project: Vec<FilePair>,    // kron-internal → 项目内
    pub to_internal: Vec<FilePair>,   // 项目内 → kron-internal
    pub conflicts: Vec<FilePair>,     // 需用户决策
    pub internal_only: Vec<FilePair>, // 项目内被删，需标记
    pub project_only: Vec<FilePair>,  // Kron 内部被删，需恢复
    pub synced: Vec<FilePair>,         // 已同步
}

pub async fn scan_all(
    storage: &Arc<dyn StorageBackend>,
    important_repo: &Arc<dyn ImportantRepo>,
    project_path: &Path,
) -> Result<ScanResult, SyncError> {
    let index = important_repo.load(project_path).await?;
    let mut result = ScanResult::default();

    for (rel_path, meta) in &index.files {
        let project_path = project_path.join(&meta.relative_path);
        let internal_path = project_path
            .parent()
            .unwrap()
            .join(".kron-internal/important/files")
            .join(&meta.relative_path);

        let direction = decide_sync_direction(
            storage.as_ref(),
            &project_path,
            &internal_path,
            meta.sync_state,
        )?;

        let pair = FilePair {
            project_path,
            internal_path,
            project_mtime: meta.added_at,
            internal_mtime: meta.added_at,
            sync_state: meta.sync_state,
        };

        match direction {
            SyncDirection::ProjectToInternal => result.to_internal.push(pair),
            SyncDirection::InternalToProject => result.to_project.push(pair),
            SyncDirection::Conflict => result.conflicts.push(pair),
            SyncDirection::AlreadySynced => result.synced.push(pair),
            SyncDirection::SourceNotFound => {
                // 双方都不存在 → 调用方清理索引
            }
        }

        // 单独检测单边缺失（上面的逻辑已经覆盖，但 internal_only/project_only
        // 需要更细致的判定 → 见 §3.4）
        let project_exists = storage.exists(&pair.project_path);
        let internal_exists = storage.exists(&pair.internal_path);
        if !project_exists && internal_exists {
            result.internal_only.push(pair.clone());
        }
        if project_exists && !internal_exists {
            result.project_only.push(pair);
        }
    }

    Ok(result)
}
```

### 3.4 单边缺失的处理矩阵

| 项目内 | Kron 内部 | 状态 | 守护进程动作 | 用户动作 |
|--------|-----------|------|-------------|---------|
| ✅ | ✅ | Synced / 待同步方向判定 | 按方向同步 | — |
| ❌ | ✅ | InternalOnly | **不动作**，标记状态 | `kron important restore` 或 `kron important remove` |
| ✅ | ❌ | ProjectOnly | **自动从项目内恢复内部副本**，标记 Synced | — |
| ❌ | ❌ | 已失效 | 从 `ImportantFilesIndex` 移除（提示用户）| `kron important remove` 或重新 add |

**为什么 InternalOnly 不自动恢复？**

用户在外部编辑器误删、临时移动、git checkout 切到旧版本——这些都是合法操作，自动从 Kron 内部"恢复"会覆盖用户的合法意图。**用户必须显式 `restore`**。

## 4. 同步执行

### 4.1 同步流程（正常路径）

```rust
// kron-sync/src/sync.rs

use chrono::Utc;
use crate::{conflict::backup_conflict, decision::decide_sync_direction};

pub async fn sync_one(
    storage: &Arc<dyn StorageBackend>,
    important_repo: &Arc<dyn ImportantRepo>,
    project_path: &Path,
    rel_path: &str,
    event_bus: &Arc<KronEventBus>,
) -> Result<SyncResult, SyncError> {
    let index = important_repo.load(project_path).await?;
    let meta = index.files.get(rel_path).ok_or_else(|| SyncError::FileNotFound(rel_path.to_string()))?;

    let project_path = project_path.join(rel_path);
    let internal_path = compute_internal_path(project_path.parent().unwrap(), rel_path);

    // Step 1: 决策
    let direction = decide_sync_direction(storage.as_ref(), &project_path, &internal_path, meta.sync_state)?;

    // Step 2: 发布 SyncStarted
    event_bus.publish(KronEvent::SyncStarted(SyncStarted {
        relative_path: rel_path.to_string(),
        direction,
        timestamp: Utc::now(),
    }));

    // Step 3: 标记 Syncing
    important_repo.update_sync_state(project_path.parent().unwrap(), rel_path, SyncState::Syncing).await?;

    // Step 4: 按方向执行
    let result = match direction {
        SyncDirection::ProjectToInternal => {
            sync_project_to_internal(storage, &project_path, &internal_path).await?;
            SyncOutcome::Synced
        }
        SyncDirection::InternalToProject => {
            sync_internal_to_project(storage, &internal_path, &project_path).await?;
            SyncOutcome::Synced
        }
        SyncDirection::AlreadySynced => SyncOutcome::Synced,
        SyncDirection::SourceNotFound => SyncOutcome::Removed,
        SyncDirection::Conflict => {
            // 详见 §5 冲突处理
            let record = create_conflict_record(
                rel_path, &project_path, &internal_path,
                storage.mtime(&project_path)?,
                storage.mtime(&internal_path)?,
            )?;
            backup_conflict(storage, &record).await?;
            important_repo.update_sync_state(project_path.parent().unwrap(), rel_path, SyncState::Conflict).await?;
            event_bus.publish(KronEvent::ConflictDetected(ConflictDetected {
                relative_path: rel_path.to_string(),
                project: project_path.parent().unwrap().to_path_buf(),
                conflict_id: record.id.clone(),
                timestamp: Utc::now(),
            }));
            SyncOutcome::Conflict(record.id)
        }
    };

    // Step 5: 标记 Synced（除非 Conflict）
    if matches!(result, SyncOutcome::Synced) {
        important_repo.update_sync_state(
            project_path.parent().unwrap(),
            rel_path,
            SyncState::Synced,
        ).await?;
    }

    // Step 6: 发布 SyncCompleted
    event_bus.publish(KronEvent::SyncCompleted(SyncCompleted {
        relative_path: rel_path.to_string(),
        direction,
        result: result.clone(),
        timestamp: Utc::now(),
    }));

    Ok(SyncResult { direction, outcome: result })
}
```

### 4.2 原子写保证

```rust
// kron-sync/src/sync.rs

use std::fs;
use tempfile::NamedTempFile;

pub async fn sync_project_to_internal(
    storage: &dyn StorageBackend,
    src: &Path,
    dst: &Path,
) -> Result<(), SyncError> {
    // 确保目标目录存在
    if let Some(parent) = dst.parent() {
        storage.create_dir_all(parent)?;
    }

    // 读取源
    let data = storage.read(src)?;

    // 写入临时文件
    let tmp = dst.with_extension(format!("{}.tmp",
        dst.extension().and_then(|s| s.to_str()).unwrap_or("")));
    storage.write(&tmp, &data)?;

    // 原子重命名
    fs::rename(&tmp, dst).map_err(SyncError::Io)?;

    Ok(())
}
```

**原子写的重要性**：同步过程中，如果直接写目标文件被中断（崩溃、断电），目标文件可能变成半写状态。**始终先写 `.tmp` 再 `rename`**——`rename` 在同一文件系统上是原子的。

### 4.3 批量同步

```rust
// kron-sync/src/batch.rs

pub struct BatchSyncOptions {
    pub fail_fast: bool,                  // 遇冲突立即停 vs 收集所有冲突
    pub max_concurrent: usize,            // 并发数（默认 4）
    pub skip_conflicts: bool,             // 跳过冲突只同步无冲突的
}

pub async fn sync_all(
    storage: &Arc<dyn StorageBackend>,
    important_repo: &Arc<dyn ImportantRepo>,
    project_path: &Path,
    options: BatchSyncOptions,
    event_bus: &Arc<KronEventBus>,
) -> Result<BatchSyncResult, SyncError> {
    let scan = scan_all(storage, important_repo, project_path).await?;
    let semaphore = Arc::new(Semaphore::new(options.max_concurrent));

    let mut tasks = vec![];

    // 无冲突的同步任务
    for pair in scan.to_internal.iter().chain(scan.to_project.iter()) {
        let permit = semaphore.clone().acquire_owned().await?;
        let storage = storage.clone();
        let repo = important_repo.clone();
        let path = project_path.to_path_buf();
        let rel = relative_from_project(&pair.project_path, &path);
        let events = event_bus.clone();
        tasks.push(tokio::spawn(async move {
            let _permit = permit;
            sync_one(&storage, &repo, &path, &rel, &events).await
        }));
    }

    // 收集结果
    let mut successes = 0;
    let mut failures = vec![];
    for task in tasks {
        match task.await {
            Ok(Ok(_)) => successes += 1,
            Ok(Err(e)) => failures.push(e),
            Err(e) => failures.push(SyncError::TaskJoin(e.to_string())),
        }
    }

    Ok(BatchSyncResult {
        scanned: scan.to_internal.len() + scan.to_project.len() + scan.conflicts.len(),
        synced: successes,
        conflicts: scan.conflicts,
        failures,
    })
}
```

## 5. 冲突处理

### 5.1 冲突检测流程

```
文件保存触发文件监听
        ↓
守护进程检查：是否为重要文件？
        ↓ 是
守护进程：1. 计算项目内 hash
         2. 读取 Kron 内部 hash
         3. 比较
        ↓ hash 不同
守护进程：4. 启动冲突检测
         5. 创建 ConflictRecord
         6. 备份双方字节副本到 kron-internal/conflicts/<id>/
         7. 更新 ImportantFileMeta.sync_state = Conflict
         8. 发布 ConflictDetected 事件
         9. **立即返回**（不阻塞、不等决策）
        ↓
订阅者各自行动：
  - GUI：弹窗提示用户（仅展示，不解决）
  - CLI：人类用户看到 ConflictDetected 日志（仅展示，不解决）
  - AI：通过轮询 `kron conflict list --json` 主动拉取并决策
```

**关键原则：守护进程是"哨兵"，不是"裁判"。**

- 检测 → 标记 → 发事件 → 返回，整个链路**无阻塞、无等待、无超时**。
- 任何决策（用户/GUI/AI）都通过 **CLI 命令同步调用**完成，不通过事件回调异步驱动（避免回调地狱和状态机混乱）。
- ConflictDetected 事件只用于**通知**，订阅者不能"替"调用方决策。

### 5.1.1 冲突决策时序图

```
    编辑器          守护进程           索引/备份             AI / CLI
     │                │                  │                    │
     │── save(file) ─→│                  │                    │
     │                │── hash 检查 ──→  │                    │
     │                │   冲突！         │                    │
     │                │── 创建 record ─→ │                    │
     │                │── 备份双方 ────→ │                    │
     │                │── 状态 Conflict →│                    │
     │                │── publish event ─────────────────→   │
     │                │   (通知用)       │                    │
     │                │                  │   ┌── 轮询 ──→   │
     │                │                  │   │              │
     │                │                  │   │  拉取冲突列表│
     │                │                  │   │  拉取 diff   │
```

注意：**守护进程不发起对 AI 的回调**。AI 通过**轮询**或**事件后主动查询**获取冲突，自主决定是否解决。AI 工作流示例见 § 5.7。

### 5.7 Heuristic 模式自动决策（v1 可选）

如果用户在 Project 配置中选了 `Heuristic`，可应用以下规则：

| 规则 | 描述 |
|------|------|
| R1 | 如果项目内 mtime 比 Kron 内部 mtime 新超过 N 秒（默认 60），保留项目内 |
| R2 | 如果 Kron 内部 mtime 比项目内 mtime 新超过 N 秒，保留 Kron 内部 |
| R3 | 如果两边 mtime 差距在 N 秒以内，标记为真冲突，转人工 |
| R4 | 如果项目内 hash 匹配 Kron 内部最近一次"备份成功"的 hash，标记为 no-op（同步无变化） |

**v1 默认 Manual**，Heuristic 是可选开关，留 v2。

### 5.8 CLI 的 AI 友好约定

Kron CLI 的设计目标是 **AI 一等公民**。所有命令必须满足以下约定。

#### 5.8.1 全局输出 flag

每个命令都支持三个输出控制 flag：

| Flag | 作用 | 默认 |
|------|------|------|
| `--json` | 输出结构化 JSON，AI 友好 | 关（人类友好）|
| `--no-color` | 去除 ANSI 颜色码 | 检测到非 TTY 时自动 |
| `--quiet` | 仅返回退出码，stdout 空 | 关 |

**环境变量**：

| 变量 | 作用 | 等价 flag |
|------|------|----------|
| `KRON_OUTPUT=json` | 默认 JSON 输出 | `--json` |
| `KRON_NO_COLOR=1` | 默认无颜色 | `--no-color` |
| `KRON_QUIET=1` | 默认安静模式 | `--quiet` |

> **设计取舍**：默认人类友好而非 JSON。人类误用 `kron` 时不应被 JSON 难住；AI 可显式 `--json` 或设环境变量。

#### 5.8.2 语义化退出码

```rust
// kron-cli/src/exit_code.rs

#[repr(u8)]
pub enum ExitCode {
    Success         = 0,   // 成功
    UserError       = 1,   // 用户错误（参数错、文件不存在）
    SystemError     = 2,   // 系统错误（IO、权限、磁盘满）
    ConflictPending = 3,   // 操作期间检测到冲突，需决策（未完成）
    PartialSuccess  = 4,   // 批量操作中部分失败
    LockHeld        = 5,   // 守护进程锁被占（另一个实例在跑）
    NotInitialized   = 6,  // 项目未初始化（kron init 未运行）
}
```

**AI 脚本可基于退出码决定下一步**（无需解析输出）：

```bash
result=$(kron task done TASK-001 --json)
ec=$?
case $ec in
    0)             echo "OK";;
    1|2)           echo "FAIL: $result"; exit 1;;
    3)             echo "Conflict! Run 'kron conflict list --json'";;
    6)             echo "Run 'kron init' first"; exit 1;;
esac
```

错误输出遵循统一 schema：

**错误码清单**（v1 必须）：

| 错误码 | 退出码 | 含义 |
|--------|--------|------|
| `file_not_found` | 1 | 文件不存在 |
| `path_outside_project` | 1 | 路径在项目根外 |

#### 5.8.4 冲突详情必含结构化 diff

`kron conflict show <id> --json` 输出除双方完整 content 外，**必须包含结构化 diff**，AI 不用再跑 `diff` 工具：

```bash
$ kron conflict show 20260905_170000_abc123 --json
{
  "id": "20260905_170000_abc123",
  "file": "src/main.rs",
  "status": "pending",
  "detected_at": "2026-09-05T17:00:00Z",
  "project_version": {
    "path": "src/main.rs",
    "mtime": "2026-09-05T16:58:00Z",
    "hash": "abc123",
    "size": 542,
    "content": "fn main() {\n    println!(\"Hello, world!\");\n}\n"
  },
  "internal_version": {
    "path": ".kron-internal/important/files/src/main.rs",
    "mtime": "2026-09-05T16:59:30Z",
    "hash": "xyz789",
    "size": 612,
    "content": "fn main() {\n    println!(\"Hello, Kron!\");\n}\n"
  },
  "diff": {
    "format": "unified",
    "from_hash": "abc123",
    "to_hash": "xyz789",
    "hunks": [
      {
        "start_line": 2,
        "lines": [
          {"type": "context", "content": "fn main() {", "line": 1},
          {"type": "remove", "content": "    println!(\"Hello, world!\");", "line": 2},
          {"type": "add", "content": "    println!(\"Hello, Kron!\");", "line": 2},
          {"type": "context", "content": "}", "line": 3}

      }
```

**diff 设计要点**：

- `format: "unified"` 类似 `diff -u` 输出，AI 已熟悉
- 每个 line 含 `type`（`context` / `add` / `remove`）和 `line`（行号）
- 二进制文件：diff 字段省略，改为 `binary_preview`（hex 头 256 字节）
- 大文件（>1MB）：diff 仅返回前 100 个 hunk + 截断提示，AI 可按需 `kron conflict show <id> --json --full`

### 5.9 AI 工作流示例

#### 5.9.1 场景：AI 编辑代码遇到冲突

```bash
#!/usr/bin/env bash
# 典型 AI 工作流：编辑 → 遇到冲突 → 决策 → 解决

set -euo pipefail

# 1. 开始工作前先 ready 检查
if ! ready=$(kron ready --json); then
    case $? in
        3) echo "Blocking issues found:"; echo "$ready" | jq '.blocking_issues';;
        *) echo "Not ready: $ready"; exit 1;;
    esac
fi

# 2. AI 编辑 src/main.rs（这里用 sed 模拟，实际是 AI 工具）
echo '// AI edit' >> src/main.rs

# 3. 编辑后再次 ready 检查（守护进程可能已检测到冲突）
ready=$(kron ready --json) || {
    # 退出码 3 = 有冲突
    echo "Conflict detected after edit"
}

# 4. AI 拉取冲突详情（含 diff）
if echo "$ready" | jq -e '.blocking_issues[] | select(.type=="conflict")' >/dev/null; then
    conflict_id=$(echo "$ready" | jq -r '.blocking_issues[] | select(.type=="conflict") | .conflict_id')
    
    detail=$(kron conflict show "$conflict_id" --json)
    
    # 5. AI 分析 diff（这里是伪代码，AI 真实决策是基于 LLM）
    decision=$(echo "$detail" | jq -r '
        # 示例：自动选择 internal（Kron 内部权威源更可信）
        "use_internal"
    ')
    
    # 6. dry-run 预览
    preview=$(kron conflict resolve "$conflict_id" --use "$decision" --dry-run --json)
    echo "Will do: $(echo "$preview" | jq -c .)"
    
    # 7. 实际执行
    kron conflict resolve "$conflict_id" --use "$decision" --json
fi

# 8. 验证 ready
kron ready --json
```

#### 5.9.2 场景：批量处理多个冲突

```bash
# 列出所有 pending 冲突
conflicts=$(kron conflict list --status pending --json)

# 逐个决策（基于 diff 自动判断）
echo "$conflicts" | jq -r '.conflicts[].id' | while read -r id; do
    detail=$(kron conflict show "$id" --json)
    
    # AI 决策逻辑示例：保留项目内版本（用户编辑优先）
    kron conflict resolve "$id" --use project --json
done

# 验证全部解决
kron ready --json  # 应 ready: true
```

#### 5.9.3 场景：AI 持续监听（轮询模式）

```bash
# AI 后台长跑任务，每 30 秒检查一次冲突
while true; do
    pending=$(kron conflict list --status pending --json 2>/dev/null)
    if [ -n "$pending" ] && [ "$(echo "$pending" | jq '.conflicts | length')" -gt 0 ]; then
        echo "$pending" | jq -c '.conflicts[]' | while read -r c; do
            # 通知外部（写文件 / 发 HTTP / 打印日志）
            echo "Conflict: $(echo "$c" | jq -c .)"
        done
    fi
    sleep 30
done
```

#### 5.9.4 AI 决策策略建议

| 场景 | 建议决策 | 理由 |
|------|---------|------|
| 项目内是 AI 刚编辑的 | `--use project` | AI 自己的编辑优先 |
| Kron 内部是用户原始编辑 | `--use internal` | 用户意图优先 |
| 双方改动互不冲突（不同行/不同段）| 手动合并（v2 提供 `auto-merge`）| 保双方意图 |
| 二进制文件 | 询问用户（AI 输出候选预览）| 无法自动决策 |
| 一边是空文件 | 用非空版本 | 显然 |

> AI 的核心优势：**能基于 diff 内容做语义判断**（不只是 hash 比对），所以让 AI 决策冲突是最合理的。

### 5.10 冲突解决后的清理

解决冲突后：

1. **不自动删除 backup**。Backup 永远保留在 `kron-internal/conflicts/`，用户通过 `kron conflict cleanup --older-than Nd` 手动清理。
2. `ImportantFileMeta.sync_state` 更新为 `Synced`（或 `InternalOnly` / `ProjectOnly`，取决于决策）。
3. `ConflictRecord.status` 更新为 `Resolved`（`Ignored` 保持 Conflict 状态）。
4. 发布 `ConflictResolved` 事件。

## 5A. 借鉴 Git 的设计原则

Kron 在冲突检测与解决的设计上，**有意借鉴 Git**。Git 是这个领域最成熟、最广泛理解的工具；AI Agent 和人类都熟悉 Git 的工作流，模仿它的模式可以降低学习成本和出错概率。

### 5A.1 Git 的核心范式（Kron 借鉴清单）

| Git 设计原则 | Git 体现 | Kron 体现 |
|-------------|---------|----------|
| **冲突状态保留在工作区** | 冲突文件保留在磁盘，带 `<<<<<<<` 标记 | 双方字节副本保留在 `kron-internal/conflicts/<id>/`，原始文件不动 |
| **检测立即返回，不阻塞** | `git merge` 失败立即退出，等用户决策 | 守护进程检测冲突 → 标记 → 发事件 → 立即返回（§ 5.1）|
| **稳定机器可读输出** | `git status --porcelain`、`git diff --numstat` | `kron <cmd> --json`、结构化 diff（§ 5.8）|
| **明确的退出码** | 0=成功 / 1=冲突或错误 / 128=致命 | 7 个语义化退出码（§ 5.8.2）|
| **不主动通知** | 没有 webhook/守护进程/事件总线 | v1 不做 HTTP 端点；AI 轮询 `kron conflict list`（Q8）|
| **冲突解决是显式动作** | `git add` 显式标记已解决 | `kron conflict resolve` 显式命令 |
| **保留多方信息** | merge 时保留 base/ours/theirs 三方 | v1 保留 2 方（project + internal），v2 考虑加 base |
| **失败不破坏工作区** | merge 失败时源分支不变 | 冲突解决失败时双源保持，sync_state 不变 |

### 5A.2 Kron 改进 vs Git 的地方

| 维度 | Git | Kron | 改进理由 |
|------|-----|------|---------|
| 退出码语义化 | 3 个 | 7 个 | Kron 区分用户错误/系统错误/锁/未初始化，AI 决策更精确 |
| 退出码 3 = "有冲突待决策" | 用 1 模糊表示 | 显式 `ConflictPending` | AI 脚本无需解析输出 |
| 错误信息结构化 | 纯文本 stderr | `{code, message, context, suggestion}` JSON | AI 解析更可靠 |
| 哨兵命令 | 无（`git status` 已是最基础查询）| `kron ready`（§ 5.8.6）| 把"能否继续工作"概念显式化 |
| 配置能力 | 大量 git config 选项 | v1 保守（Q2、Q9 才用配置）| Kron v1 不重复 Git 的配置复杂度 |

### 5A.3 AI Agent 工作流对照表

| 步骤 | Git 命令 | Kron 命令 |
|------|---------|----------|
| **1. 查询状态** | `git status --porcelain` | `kron ready --json` / `kron status --json` |
| **2. 检测冲突** | `git status`（看到 `UU`）| `kron conflict list --json` |
| **3. 看冲突详情** | `cat <file>`（带冲突标记）/ `git diff` | `kron conflict show <id> --json`（含结构化 diff）|
| **4. 决策** | `git checkout --ours/theirs` 或手动编辑 | `kron conflict resolve <id> --use project/internal/both` |
| **5. 标记完成** | `git add <file>` | `kron conflict resolve <id>` 一次性完成 |
| **6. 继续工作** | `git merge --continue` / `git commit` | `kron ready --json` 验证 |

**AI Agent 学习曲线**：会 Git 就会用 Kron，命令集相似度 80%+。

### 5A.4 明确不做的事（Git 也没做）

| 不做 | 理由 |
|------|------|
| HTTP 回调通知 | Git 也没有这个机制（Q8）|
| 自动 merge 冲突 | Git 只自动 merge 不冲突的改动；冲突必手动决策 |
| 守护进程反向推送 | Git 是按需工具，不是常驻服务 |
| 复杂配置 | Git config 选项上千；Kron v1 保持精简 |

### 5A.5 v2 候选（Git 路线下）

如果 v1 反馈良好且需要扩展，**只沿 Git 路线扩展**：

| 候选 | Git 对应物 | 价值 |
|------|----------|------|
| `kron conflict base` 显示三方 | `git show :1:` | merge 类冲突更清晰 |
| `kron stash`（临时保存 AI 编辑）| `git stash` | AI 中断/恢复场景 |
| `kron log --graph` | `git log --graph --oneline` | 调试同步历史 |
| `kron reflog` | `git reflog` | 误操作恢复 |
| `kron bisect` | `git bisect` | 找出引入同步问题的提交 |

**明确不做**：

- ❌ HTTP 服务（Git 也没有）
- ❌ Webhook 推送
- ❌ 守护进程 IPC socket（v2 再考虑，先观察 v1 是否真有需求）

### 6.3 复原执行

```rust
// kron-sync/src/restore.rs

pub async fn restore_one(
    storage: &Arc<dyn StorageBackend>,
    important_repo: &Arc<dyn ImportantRepo>,
    project_path: &Path,
    rel_path: &str,
    trigger: RestoreTrigger,
    event_bus: &Arc<KronEventBus>,
) -> Result<RestoreRecord, SyncError> {
    let internal_path = compute_internal_path(project_path, rel_path);
    if !storage.exists(&internal_path) {
        return Err(SyncError::InternalCopyMissing(rel_path.to_string()));
    }

    let project_path = project_path.join(rel_path);
    let started_at = Utc::now();

    // 创建复原记录
    let mut record = RestoreRecord {
        id: format!("restore_{}_{}",
            started_at.format("%Y%m%d%H%M%S"),
            simple_hash(rel_path)),
        triggered_by: trigger,
        started_at,
        finished_at: None,
        files_restored: vec![rel_path.to_string()],
        status: RestoreStatus::Running,
    };

    // 发布 RestoreStarted 事件
    event_bus.publish(KronEvent::RestoreStarted(RestoreStarted {
        relative_path: rel_path.to_string(),
        triggered_by: trigger,
        timestamp: started_at,
    }));

    // 原子写
    let result = sync_internal_to_project(storage, &internal_path, &project_path).await;

    // 更新记录状态
    record.finished_at = Some(Utc::now());
    record.status = match result {
        Ok(()) => {
            // 标记 Synced
            important_repo.update_sync_state(
                project_path.parent().unwrap(),
                rel_path,
                SyncState::Synced,
            ).await?;
            RestoreStatus::Success
        }
        Err(e) => {
            tracing::error!("Restore failed: {}", e);
            RestoreStatus::Failed
        }
    };

    // 持久化记录
    save_restore_record(storage, &record).await?;

    // 发布 RestoreCompleted 事件
    event_bus.publish(KronEvent::RestoreCompleted(RestoreCompleted {
        relative_path: rel_path.to_string(),
        record_id: record.id.clone(),
        status: record.status,
        timestamp: record.finished_at.unwrap(),
    }));

    Ok(record)
}
```

### 6.4 守护进程自动复原（可选）

**默认关闭**。用户在 Project 配置中可开启 `auto_restore_on_external_delete: true`。

```rust
// kron-daemon/src/auto_restore.rs

pub async fn maybe_auto_restore(
    storage: &Arc<dyn StorageBackend>,
    important_repo: &Arc<dyn ImportantRepo>,
    project_config: &Project,
    rel_path: &str,
) -> Result<(), SyncError> {
    let index = important_repo.load(&project_config.path).await?;
    let meta = match index.files.get(rel_path) {
        Some(m) => m,
        None => return Ok(()),  // 不是重要文件
    };

    let project_path = project_config.path.join(rel_path);
    let internal_path = compute_internal_path(&project_config.path, rel_path);

    // 只在 InternalOnly 状态 + auto_restore 开启时自动恢复
    if meta.sync_state == SyncState::InternalOnly
        && project_config.settings.auto_restore_on_external_delete
    {
        restore_one(
            storage, important_repo,
            &project_config.path, rel_path,
            RestoreTrigger::DaemonAuto,
            &event_bus_clone(),
        ).await?;
    }
    Ok(())
}
```

## 7. 守护进程与同步的协作

### 7.1 文件监听 → 同步触发链

```
editor.save(file)
        ↓
notify::Watcher 触发 FileChanged 事件
        ↓
kron-daemon 接收
        ├── 检查：是否在 .kron-internal/ 下？ → 跳过
        ├── 检查：是否被 .gitignore 屏蔽？ → 跳过
        ├── 检查：是否是 .kron/VERTEX/*/tasks.md？ → 触发 tasks 重新解析
        ├── 检查：是否是重要文件？ → 触发 sync_one()
        └── 检查：是否在 .kron/.kron-context/ ? → 跳过（由 context 模块自己处理 TTL）
```

### 7.2 防抖

编辑器保存通常短时间内连续触发多次（如自动保存 + 手动保存）。守护进程**必须防抖**：

```rust
// kron-daemon/src/watcher.rs

use tokio::time::{sleep, Duration};
use std::collections::HashMap;
use tokio::sync::Mutex;

pub struct Debouncer {
    /// rel_path → last_pending
    pending: Arc<Mutex<HashMap<PathBuf, Instant>>>,
    debounce_ms: u64,
}

impl Debouncer {
    pub async fn debounce<F, Fut>(&self, path: PathBuf, action: F)
    where
        F: FnOnce() -> Fut,
        Fut: Future<Output = ()>,
    {
        let key = path.clone();
        {
            let mut p = self.pending.lock().await;
            p.insert(key, Instant::now());
        }

        sleep(Duration::from_millis(self.debounce_ms)).await;

        let should_run = {
            let p = self.pending.lock().await;
            p.get(&key).map(|t| t.elapsed() >= Duration::from_millis(self.debounce_ms)).unwrap_or(false)
        };

        if should_run {
            action().await;
            let mut p = self.pending.lock().await;
            p.remove(&key);
        }
    }
}
```

**默认防抖窗口**：500ms。可在 Project 配置中调整（min: 100ms, max: 5000ms）。

每 5 分钟扫描一次所有重要文件：

## 8. 边缘情况

### 8.1 边缘情况清单

| # | 情况 | 处理 |
|---|------|------|
| E1 | 文件正在被写入（编辑器保存过程中）| notify 触发时读到半写文件 → **md5 校验** + 等待稳定（`mtime` 在 100ms 内不变再算 hash）|
| E2 | 文件被外部删除同时内部修改 | 检测到双方 hash 不一致，标记 Conflict |
| E3 | Kron 内部目录被用户手动 rm -rf | 启动时检测到内部目录缺失 → 从 `ImportantFilesIndex` + 项目内重建 |
| E4 | 软链接失效（Unix）| 检测 `symlink_metadata` vs `metadata`，如果失效 → 提示用户，标记 `ProjectOnly` |
| E5 | 文件大小为 0 | 视情况：可能是合法空文件 → 正常处理；可能是写入错误 → 比较 mtime |
| E6 | 文件没有读权限 | `StorageError::PermissionDenied` → 跳过该文件，记录日志 |
| E7 | 项目根目录被移动/重命名 | 通过 `.kron-internal/config.json` 中的 `project_path` 字段校正 |
| E8 | 并发 sync 同一文件 | 用 `ImportantFileMeta.sync_state = Syncing` 标志位做锁，第二次调用直接返回 |
| E9 | 守护进程崩溃 | 崩溃时可能残留 `Syncing` 状态 → 下次启动时所有超过 5 分钟的 `Syncing` 视为 `Conflict` |
| E10 | Git pull 后项目内文件变了 | Kron **不感知** git 操作（按设计原则），由 mtime+hash 检测 |
| E11 | 磁盘满 | 同步前 `storage.write` 失败 → 回滚状态，发布 SyncFailed 事件 |
| E12 | 两个守护进程实例 | 项目根下检测 `.kron-internal/.lock` 文件，存在则拒绝第二个启动 |

### 8.2 写时稳定性检测

```rust
// kron-sync/src/stability.rs

use tokio::time::{sleep, Duration};

pub async fn wait_for_stable(
    storage: &dyn StorageBackend,
    path: &Path,
    max_wait_ms: u64,
) -> Result<(), SyncError> {
    let mut last_mtime = storage.mtime(path)?;
    let mut elapsed = 0u64;

    while elapsed < max_wait_ms {
        sleep(Duration::from_millis(50)).await;
        let current_mtime = storage.mtime(path)?;
        if current_mtime == last_mtime {
            return Ok(()); // mtime 连续两次相同，认为稳定
        }
        last_mtime = current_mtime;
        elapsed += 50;
    }

    Err(SyncError::FileNotStable(path.to_path_buf()))
}
```

### 8.3 单实例锁

```rust
// kron-storage/src/lock.rs

pub struct ProjectLock {
    path: PathBuf,
}

impl ProjectLock {
    pub fn acquire(project_path: &Path) -> Result<Self, LockError> {
        let path = project_path.join(".kron-internal/.lock");
        // 使用 fs2 crate 的 try_lock_exclusive
        let file = std::fs::OpenOptions::new()
            .create(true)
            .write(true)
            .open(&path)?;
        file.try_lock_exclusive().map_err(|_| LockError::AlreadyLocked)?;

        Ok(Self { path })
    }
}

impl Drop for ProjectLock {
    fn drop(&mut self) {
        let _ = std::fs::remove_file(&self.path);
    }
}
```

### 9.5 表格 vs JSON 的实现统一

CLI 输出层实现一个统一的 `Output` trait：

```rust
// kron-cli/src/output/mod.rs

pub enum OutputFormat {
    Human,  // 表格 + 颜色
    Json,   // 结构化 JSON
}

pub trait Output: Serialize {
    fn render(&self, format: OutputFormat) -> String {
        match format {
            OutputFormat::Human => self.render_human(),
            OutputFormat::Json => serde_json::to_string_pretty(self).unwrap(),
        }
    }
    fn render_human(&self) -> String;
}
```

每个命令定义自己的输出结构体（实现 `Serialize`），自动支持两种格式。**不会出现"忘记实现 JSON 输出"的命令**（编译期保证）。

## 10. 性能与限制

### 10.1 性能目标

| 指标 | 目标 |
|------|------|
| 单文件同步（10MB）| < 100ms（含 hash 计算）|
| 100 文件项目扫描 | < 1s |

|------|------|------|

| 不支持文件夹级别同步 | 每个重要文件单独同步 | v2 可考虑 |
| 不支持 git 操作感知 | Kron 不监听 .git | 用户手动 sync |
| 大文件（>100MB）同步慢 | md5 计算成本 | 可选 xxhash 替代 |
| 跨设备时钟偏差 | 影响 mtime 比较 | hash 最终仲裁 |

## 11. 关键不变量（Invariants）

任何同步算法都必须保证的不变量：

| # | 不变量 | 检验方式 |
|---|--------|---------|
| I1 | 同一时刻，每个文件至多有一个 sync 操作在执行（Syncing 标志位）| `ImportantFileMeta.sync_state` |
| I2 | 同步过程失败时，目标文件不能半写（原子写 .tmp + rename）| code review |
| I3 | 冲突备份一定在 `kron-internal/conflicts/<id>/` 下完整存在 | 冲突解决前校验 |
| I4 | Kron 内部副本被外部删除时自动从项目内恢复（不丢数据）| health check |
| I5 | 项目内被外部删除时不自动恢复（保护用户意图）| health check |
| I6 | 冲突解决前，两份字节副本必须保留 | backup_conflict 在前 |
| I7 | `ImportantFilesIndex` 中每个 path 必须对应一份真实存在的副本（Kron 内部或项目内，至少一个）| 启动校验 |

## 12. 与其他模块的边界

### 12.1 `kron-sync` 依赖

```rust
// kron-sync/Cargo.toml

[dependencies]
kron-core = { path = "../kron-core" }
tokio = { workspace = true }
tracing = { workspace = true }
```

**`kron-sync` 不依赖任何其他模块**。所有数据访问通过 `kron-core::ports::StorageBackend` 和 `ImportantRepo`。

### 12.2 谁能调用 `kron-sync`

| 调用方 | 调用方式 |
|--------|---------|
| `kron-cli` 的 `important` / `conflict` 子命令 | 直接调用 `SimpleSyncStrategy` 方法 |
| `kron-gui` 的 Tauri commands | 同上 |
| `kron-daemon` 的 watcher / health_check | 通过 `handles.sync` 调用 |
| `kron-context` | ❌ 不调用（context 模块只看 git，和 sync 无关）|
