## 1. 动机

### 1.1 背景

AGENTS.md §"Access layers" 第 122 行已声明 LSP 是 v1.3+ 入口 (之前是"不在 v1 必需范围" — 2026-10-07 改向). 

LSP (Language Server Protocol) 服务的**标准能力**是给编辑器侧 (VSCode / Cursor / Neovim) 提供:
- **Hover** — 鼠标悬停 `// @kron:intent <slug>` 时, 显示该 intent 的标题 + 摘要
- **Definition** — 从锚点跳到 `.kron/intents/<slug>.md` 文件
- (可选) **Completion** — 输入 `// @kron:intent <Tab>` 补全已有 slug
- (可选) **Diagnostics** — 锚点指向不存在 intent 时画红线 (与 `kron lint` 规则 A-class 等价)

**问题**: Go 生态**没有**官方 LSP SDK (微软官方只出 Node / Python / Rust / C#), 需要**从社区选一个**, 选错会被**协议兼容性问题**反复折腾.

### 1.2 目标

本 RFC 只回答**一件事**: **LSP 协议层**用哪个 Go SDK? 锁定后**不**再换.

**不**在本 RFC 范围:
- LSP 服务的**业务逻辑** (hover 拿什么 / completion 怎么排) → 走 `docs/implementation/lsp.md` (本 PR 同步新建)
- 协议版本选 (3.17 vs 3.18) → §4 选 SDK 时**顺带**拍
- 跨语言 client 端 SDK 选 (VSCode extension / Cursor config) → 走 `docs/implementation/ide-interaction.md` 扩展

## 2. 候选评估

### 2.1 候选清单

| 候选 | 仓库 | Stars (近似) | 协议覆盖 | 维护 |
|---|---|---|---|---|
| **A. `go.lsp.dev/protocol`** | `go-lsp` 组织 | 1.2k+ | LSP 3.17 全 | 活跃 (2026 持续) |
| B. `gopls` (golang.org/x/tools/internal/lsp/protocol`) | 官方 | — | LSP 3.17 | 官方但**内部包** (vendor 风险) |
| C. `creachadair/lsp` | 个人 | ~200 | LSP 3.17 基础 | 维护慢 |
| D. `sourcegraph/go-lsp` | Sourcegraph | ~400 | LSP 3.16 残 | 已 archive (2024) |

### 2.2 候选逐项

**A. `go.lsp.dev/protocol`** ✅ **推荐**

- 维护: `go-lsp` 组织 (gopls 周边生态), 2026 仍在更新
- 覆盖: LSP 3.17 全, 与 `gopls` 内部使用**同一个**协议定义 (实际是 gopls 抽出来的)
- API: 类型化 (TypeScript-style), 不是裸 JSON
- 依赖: 极少 (charmbracelet/log 可选)
- License: MIT

**B. `golang.org/x/tools/internal/lsp/protocol`** ❌

- 内部包 (`internal/`), 不能**直接** import — `go.mod` replace vendor
- 与 Go 版本强绑定, 升级 Go 时可能爆
- **不**是给应用层用, 是给 `gopls` 内部用

**C. `creachadair/lsp`** ❌

- 协议覆盖薄 (没有 `textDocument/definition` 的完整类型)
- 维护频次低
- 社区小

**D. `sourcegraph/go-lsp`** ❌

- **已 archive** (2024 年)
- LSP 3.16 残, **不**支持 3.17
- 锁**已死**项目 = 协议漏洞**永远**等不到修

---

## 3. 决策

**选 A. `go.lsp.dev/protocol`**.

理由:
1. 与 `gopls` 共享协议定义 → 类型一致, 调试时**不会**走"两份协议不兼容"坑
2. 维护活跃, 2026 仍在 commit
3. API 类型化 → 写 `serve-lsp` 时**不**用裸 `map[string]any`
4. MIT 协议, 仓库**不**会被迫换 license
5. AGENTS.md §"off-limits" 已加 "新 top-level dep 走 explicit approval" → 本 RFC 即**就是**那个 approval

**决策约束** (与 `docs/process/new-access-layer.md` 一致):
- 一旦选 A, **不**在 v1.3 周期内换. 换 = 重写 serve-lsp 协议层
- 任何"为什么不用 B/C/D"的 PR 讨论 = 引用本 RFC §2.2, **不**重新开评估

## 4. 协议版本 + transport

### 4.1 协议版本

- **LSP 3.17** (主流编辑器都支持, VSCode 1.85+ / Cursor / Neovim nvim-lspconfig)
- 客户端会在 `initialize` 请求里发 `client.capabilities` + `client.info.version`; 服务端**不**强制版本, 但**只**实现 3.17 子集

### 4.2 transport

- **stdio** (类似 MCP) — 简单, 编辑器侧 child process
- 未来**不**考虑 socket (LSP over TCP 不是主流 client 习惯)

## 5. 业务能力范围 (v1.3 第一版)

| LSP method | 实现? | 数据来源 | 备注 |
|---|---|---|---|
| `initialize` | ✅ | 静态 | 报 server name / version / capabilities |
| `textDocument/hover` | ✅ | `internal/parser.ScanAnchors` + `internal/store.Get` | hover `// @kron:intent <slug>` → 显示 intent 标题 + summary |
| `textDocument/definition` | ✅ | `internal/parser.ScanAnchors` + `internal/store.Get` | 跳到 `.kron/intents/<slug>.md` 文件路径 |
| `textDocument/completion` | ⏳ v1.4+ | `internal/store.List` | 补全已有 slug |
| `textDocument/publishDiagnostics` | ⏳ v1.4+ | `internal/lint.Run` (A-class) | 与 CLI lint A-class 共用 |
| `shutdown` / `exit` | ✅ | 静态 | 正常退出 |

v1.3 **不**做: completion / diagnostics. v1.4+ 评估.

## 6. 调用 `internal/` 边界

`cmd/kron/serve-lsp/` **只**调 `internal/parser` + `internal/store`. **不**调 `internal/lint` (v1.3 不发 diagnostics).

`internal/parser` 需**新加**的 API (走 `docs/process/new-internal-api.md`):
- `func AnchorAtPosition(file string, line, col int) (slug string, ok bool)` — 给 hover/definition 定位

---

## 7. 不兼容风险

- **编辑器的 LSP client 版本老** (3.16-) → 服务端 3.17 子集, **不**影响 — 3.16 client 只会用 3.16 子集能力
- **`go.lsp.dev/protocol` 突然断更** → fallback 是 `gopls` 内部包 (B), 但走 vendor. 概率低 (`go-lsp` 组织是 gopls 团队外围)
- **LSP 4.0 发布** → 服务端 `initialize` 报 3.17, **不**升级; client 4.0 降级到 3.17 — LSP 协议**不**像 HTTP 那样硬版本
