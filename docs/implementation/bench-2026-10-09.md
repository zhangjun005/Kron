# MCP 性能基线（2026-10-09）

> 数据来源：`cmd/kron/serve-mcp/bench_test.go` 的 `TestBenchReport`。
> 测试方式：在 10 / 100 / 500 intent 三个规模上对**每个**工具调一次，
> 跑 3 次取裁尾均值（drop 最高，剩 2 取平均）。
> 总耗时：20.5s（含 3 规模 × 13 工具 × 3 runs）。
>
> 用途：未来 PR 改动 MCP handler 后的**回归基准**。scale ratio 超过 baseline +20%
> 视为需要调查；超过 +50% 视为必须 explain。

## 2. 工具分类

按 scale 比率分三组：

### 2.1 **O(1) 元数据 / 写**（4 工具）— scale ≤ 1.0x

| 工具 | 用途 | 性能 |
|---|---|---|
| `kron_init` | 创建 `.kron/` 骨架 | ~256µs |
| `kron_restore` | 从 trash 还原 | ~256µs |
| `kron_add` | 写新 intent | ~60ms（写文件 + 重读校验，**与 N 无关**）|
| `kron_update` | 改 intent | ~6ms（读 + 改 + 写，**与 N 无关**）|

**结论**：这 4 个**不是**瓶颈。`kron_add` 60ms 看着高，但 500 intent 时仍 60ms——这是**单文件写**成本（fsync + parser 校验），不能通过 N 优化。

### 2.2 **每次都重 walk 全部 intent**（9 工具）— scale 21-40x ⚠️

| 工具 | 500 intent 时长 | 缩放 |
|---|---:|---:|
| `kron_assume_check` | 47.4ms | 39.9x |
| `kron_intent_density` | 49.2ms | 39.3x |
| `kron_stale` | 54.2ms | 36.0x |
| `kron_impact` | 50.4ms | 28.7x |
| `kron_list` | 51.3ms | 28.8x |
| `kron_tree` | 58.9ms | 28.2x |
| `kron_lint` | 50.3ms | 28.0x |
| `kron_delete` | 49.0ms | 26.0x |
| `kron_get` | 47.3ms | 21.5x |

**这 9 个工具的共同模式**：
- 每次调用都 `store.NewReader(root).LoadAll(ctx)` ——全 intent 从 disk 读 + parse
- 多数再叠加 `parser.ScanAnchors` / `parser.ScanMarkdownAnchors` ——全 source tree 走一遍
- `kron_lint` / `kron_intent_density` / `kron_assume_check` 还要走 2 套 scan

**50ms 主体组成**（粗略）：

- 10 intent：~1ms（parse overhead，walk cost 不显）
- 500 intent：~50ms（500 文件的 os.ReadFile + yaml.Unmarshal + walk）
- 估算单文件：~100µs（read + parse + 内存分配）

## 3. 慢的根因（已定位）

每个 handler 路径里：

```
handler
  → store.NewReader(root)        // 每次都 new
  → r.LoadAll(ctx)               // 每次都 read all .md + yaml parse
  → [scan] parser.ScanAnchors(root)  // 每次都 walk source tree
  → [scan] parser.ScanMarkdownAnchors(root)
  → 计算 relations / lint / 等
  → 返回 wire shape
```

**没有任何缓存**。`store.NewReader` / `r.LoadAll` 也没考虑 mtime invalidation（**当前是 `internal/store` 的设计选择**——见 [`docs/abstractDesign/architecture.md` §〇 铁律 #5](../../docs/abstractDesign/architecture.md) "CI lint 是唯一的门禁"）。

## 4. 优化候选（按 ROI 排序，**不**预排）

按 `docs/process/new-internal-api.md`，**任何**优化都要先论证，**不**主动加。下面只是 ROI 排序：

| # | 优化 | 影响工具 | 预期提升 | 风险 |
|---|---|---|---|---|
| **OPT-1** | 在 `serve-mcp` 层加 per-call `LoadAll` cache（用 `singleflight` + `mtime` invalidation）| 9 个慢工具 | 500 intent 时 **50ms → <1ms**（hit cache）| cache 一致性；按 [`internal-discretion.md`](../process/internal-discretion.md) 4 问，留 serve-mcp 不下沉 |
| **OPT-2** | `kron_lint` / `kron_intent_density` 共享同一次 anchor scan | kron_lint + kron_intent_density | 单次调用 -10ms | handler 间共享状态；按 [`internal-discretion.md`](../process/internal-discretion.md) Q1（**现在**只 2 调用方，且不在同次 call——不沉，留 serve-mcp）|
| **OPT-3** | `kron_tree` / `kron_impact` / `kron_get` 走 `view.IntentTree` 共享内存 | 3 个工具 | 500 intent 时 -20ms | view 已是 internal；handler 层加 LRU |
| **OPT-4** | `kron_assume_check` 单独缓存 `assumption.Reader` | kron_assume_check | 500 intent 时 -5ms | registry 改动频次低，TTL 5s 可 |

**优先级建议**：**OPT-1** 单点改性能提升 50x（500→<1ms），且 risk 受 singleflight 限制——**最值得做**。**OPT-2** 性价比次之（只省一次 scan）。**OPT-3 / OPT-4** 是局部优化。

**约束**（`docs/process/internal-discretion.md` §1）：这 4 个优化**都**不**下**沉到 `internal/`——它们都是 serve-mcp 内的 cache 策略，**留**在访问层。`internal/` 不做 cache（铁律 #5）。


## 6. 下次再跑怎么对比

`TestBenchReport` 输出**全工具表格** + **scale ratio 表**。对比方法：

1. 跑 `TestBenchReport` 取 500 intents 列
2. 对比 baseline（本文档）每个工具的耗时
3. 单工具 +/-20% 需调查；+/-50% 必查 PR
4. scale ratio（500/10）是**结构性指标**——如果某工具 scale 突然从 28x 跳到 50x，意味着该 handler 改坏了"不重 walk"的不变量

## 7. WHY 写这份报告

按 user 2026-10-09 原话：

> "目前的 mcp 工具都测试一下，并且我要详细的测试数据，主要是看一下哪一些运行比较慢"

→ 答：
- 9 个**读类**工具都慢（kron_lint / kron_list / kron_get / kron_impact / kron_tree / kron_stale / kron_delete / kron_intent_density / kron_assume_check），500 intent 时 **47-59ms**
- 4 个**写类**工具都**不**慢（kron_add / kron_update / kron_init / kron_restore），**与 intent 数量无关**
- 慢的根因：**每次都重 walk**（不 cache）。`internal/store` 当前**不**做 cache（铁律 #5）
- 优化 ROI：OPT-1（per-call LoadAll cache）单点改 50x 提升，但**不**预排——等 user 决定
