## 重要设计原则

1.数据处理上，一切必须存储在当前仓库里，禁止往工具自有目录塞项目数据
2.想法设计上，备份，行进全部依赖git，不要做任何的自备份想法

### 一、 核心定位与设计哲学

- **系统定位**：面向个人开发者在 AI 辅助开发场景下的轻量级任务追踪与代码意图管理系统。
- **极简原则**：反思kron早期设计中的双源同步与常驻守护进程等复杂机制，倾向于采用基于本地文件的单一数据源（Single Source of Truth），降低系统复杂度与维护成本。
- **技术演进方向**：技术栈目前倾向于从前期的 Rust/Tauri 原型转向 Go 语言+typescript重构，以换取更平缓的开发曲线与高效的文件处理能力。
- **解决的痛点**：尝试缓解 AI 辅助编程带来的代码可维护性下降、认知负荷过载（Cognitive Debt）以及代码中设计意图/决策权衡丢失（Intent Debt）的问题。

---

### 二、 意图（Intent）的表达与存储机制

- **代码端微锚点（当前构想）**：采用类似软注解的轻量注释（如 `// @kron:intent`），作为代码与意图文档之间的连接指针，避免在源码中堆砌长篇说明。
- **正文持久化载体**：详细的设计目标、权衡考量（Trade-offs）与边界假设，倾向于存放在仓库本地的 Markdown 文件中，利用 Front-matter 记录结构化元数据。
- **多语言适配策略**：
- *基础方案*：依靠基于常见注释前缀（如 `//`, `#`）的规则匹配，实现跨语言的基础行级扫描。
- *进阶/备选方案*：深层符号绑定可结合 Agent 主动上报、Tree-sitter 语法树解析或针对特定语言的轻量 AST 解析。

---



### 三、 AI 协同与协议扩展（MCP）

- **解耦原则**：系统本身可不直接绑定大模型 API，而是将自身定位为数据与上下文管理层。
- **协议化交互探索**：考虑通过接入 MCP（Model Context Protocol）等标准化工具协议，为外部的架构规划或编码智能体（如 Cursor、Claude Code）提供意图的起草、检索与校验能力。

---



### 四、 意图分析树（Intent Tree）的设计方向

- **拓扑建模思路**：可通过在元数据中引入 `parent`（所属层级）或 `depends_on`（依赖关系）等可选字段，将离散的意图组织为反映模块拆解或逻辑依赖的拓扑结构（DAG）。
- **关系推导途径**：
- *方案 A（显式规划）*：由开发者或架构设计 Agent 在分解任务阶段显式指定上下级关联。
- *方案 B（静态推导）*：由分析工具通过对代码符号调用或文本引用的交叉匹配，辅助推导意图间的引用链路。
- **GUI 呈现探索**：客户端可考虑提供层级折叠树或调用/影响流视图，用于辅助人类审查潜在的改动影响。

---



### 五、 IDE 内部的悬停与交互方案

- **核心目标**：在编辑器中把光标移至特定意图注释上方时，能以富文本（Hover）形式展示其背后的结构化意图内容。
- **实现路径对比**：
- *路径 1（独立扩展）*：编写针对 VSCode / Cursor 的专属轻量插件，通过监听文本行并读取对应 Markdown 文件实现快速验证。
- *路径 2（标准协议）*：封装为轻量 LSP（Language Server Protocol）服务进程，实现通用的 `textDocument/hover` 接口，以便跨多款主流编辑器复用。
- **交互延伸可能**：悬停弹窗内除只读展示外，可根据需要探索深层跳转（唤起客户端）或携带意图上下文唤起 AI 交互等增强操作。
